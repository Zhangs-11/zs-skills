# change-meeting-brief

> 开会时真正需要的不是一份技术方案，而是几十秒内把“出了什么问题、为什么、怎么解决”讲明白。

change-meeting-brief 会读取需求、PR 或 Review 文档，只保留一条业务因果链，默认输出三句话、约 20～40 秒的会议口径。

## 安装

```bash
npx skills add Zhangs-11/zs-skills --skill change-meeting-brief
```

## 你可以这样说

- “这个需求上线前我要简单汇报一下，帮我压成三句话。”
- “会上怎么讲？只说问题、原逻辑和这次怎么解决。”
- “根据这份 review 文档写一段 30 秒口径，不讲代码。”
- “给产品同学能听懂的版本。”

## 默认输出

```text
问题：什么场景下出现了什么错误，造成什么影响。
改之前：原逻辑怎么处理，为什么会触发这个问题。
这次修改：现在怎么处理，为什么能避免问题。
```

## 前置条件

- [ ] 至少提供需求、PR、Review 文档或一段包含问题和方案的说明。
- [ ] 如果要使用“已经解决”的确定口径，应有测试或运行证据；否则默认使用保守表述。
- [ ] 如听众是产品、研发或上线会议参与者，可在请求中注明以调整术语。

## 边界

- 默认只返回一小段，不生成文件，不附调查过程和测试清单。
- 优先说功能和用户结果，不念函数、文件和提交列表。
- 没有验证过的根因不会写成确定事实；只有静态方案时使用“用于避免”等保守表达。
- 如果需要完整 Review 交接文档，应使用 `review-handoff`。

## Troubleshooting

| 问题 | 解决方法 |
|---|---|
| 输出仍然像技术方案 | 明确说“面向产品，只保留三句话，不讲文件和函数” |
| 材料只有重构，没有实际问题 | 先补充可观察目标；Skill 不会把重构编造成问题修复 |
| 一段话超过 40 秒 | 只保留一个主要问题和一条因果链，其他影响另行说明 |

完整压缩规则见 [SKILL.md](SKILL.md)。
