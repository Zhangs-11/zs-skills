# diagnose-and-explain

> 报错消失不代表问题解决了；一个听起来合理的原因，也不等于真正的根因。

`diagnose-and-explain` 会先读代码、日志、配置、数据和业务规则，再用可复现信号、正常对照和多个可证伪假设查明问题。它不仅适用于技术 Bug，也覆盖数据异常、业务问题、产品问题和流程故障，并默认把用户当作第一次接触这个领域的人来解释。

## 安装

```bash
npx skills add Zhangs-11/zs-skills --skill diagnose-and-explain
```

查看仓库中可发现的 Skill：

```bash
npx skills add Zhangs-11/zs-skills --list
```

安装后新开一次 Claude Code、Codex 或其他兼容 Agent Skills 的会话。

## 你可以这样说

- “这个接口为什么偶发超时？先只读调查，找到根因并给我讲明白，不要直接改代码。”
- “最近退款率突然升高，帮我从数据、业务规则和流程上分析原因。”
- “这个产品流程为什么总在审批环节卡住？把我当小白解释，复杂关系可以画图。”
- “先区分事实、推断和未知，修复方案等我确认后再执行。”

## 它怎样避免拍脑袋诊断

```text
固定期望与实际现象
        ↓
读取最新事实源和正常对照
        ↓
建立安全的复现或证据闭环
        ↓
提出多个可证伪候选原因
        ↓
寻找反证并逐步排除
        ↓
用人话、例子或图讲清因果链
        ↓
展示建议并等待修复授权
```

无法稳定复现时，它不会硬猜，也不会直接停止。一次性线上事故可以通过时间线、审计记录和多源交叉验证形成高可信推断，但会明确标注证据缺口和结论强度。

## 前置条件与边界

- [ ] 使用支持 Agent Skills 的工具，并安装 `first-principles-adversarial-review` 作为推理底盘。
- [ ] 尽量为 Agent 提供代码、日志、配置、数据只读结果或业务规则等事实源。
- [ ] 默认调查只读；可能触发真实业务、污染数据或写入外部状态的复现，需要先确认。
- [ ] 找到根因不等于获得修复授权。修改代码、配置、测试、文档或数据，以及提交、推送和部署，都必须另行确认。

本 Skill 没有固定的语言或框架依赖，也不要求所有问题都能写成自动化测试。

## 与其他 Skill 的区别

| Skill | 主要目标 |
|---|---|
| `diagnose-and-explain` | 找到既有问题的根因，并把因果链讲明白 |
| `clarify-before-action` | 在开始新需求或复杂任务前澄清要做什么 |
| `explain-to-master` | 通过复述、反例和迁移测试，让用户真正掌握一个主题 |
| `first-principles-adversarial-review` | 为各种实质性任务提供事实核验、机制推导和反证底盘 |

## Troubleshooting

| 问题 | 原因 | 解决方法 |
|---|---|---|
| 结论只有“可能是……” | 缺少日志、代码、配置或业务事实源 | 提供可读取材料，或要求明确列出缺失证据和最短验证路径 |
| Agent 看到报错就给修复代码 | 没有停在诊断确认点 | 明确说“只读诊断，修复前先向我确认拟修改范围” |
| 无法复现就停止分析 | 把技术调试流程错误套到了所有场景 | 要求改用时间线、正常对照、审计记录和多源交叉验证 |
| 解释太专业看不懂 | 没有解释首次出现的术语和关键方法 | 要求“把我当小白，先用一句人话总结，复杂关系画图” |

完整执行方法见 [SKILL.md](SKILL.md)。
