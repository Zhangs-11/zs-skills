# review-handoff

> PR 已经写完，但如果同事还要从零猜“为什么改、改了什么、重点看哪里”，Review 时间并没有真正省下来。

review-handoff 会读取一个或多个 CodeUp PR，把需求背景、问题、根因、修复方案和验证边界整理成可直接转发的 Markdown 文档，并在最上方列出仓库与对应 PR。

## 安装

```bash
npx skills add Zhangs-11/zs-skills --skill review-handoff
```

## 你可以这样说

- “这是我的 PR，帮我生成一份 MD 给同事 review。”
- “这个需求改了三个仓库，把仓库和 PR 都放在文档最上面。”
- “根据当前 diff 整理背景、问题根因和改前改后，重点提醒同事看状态恢复。”
- “我只给你 PR，你先从代码和关联需求恢复上下文。”

## 你会得到

- 仓库与 PR 的清晰映射；
- 零背景也能理解的需求背景、问题和根因；
- 按业务链路整理的改动前/后表；
- 影响范围、已验证/未验证事项；
- 2～4 个具体的 Review 重点。

文档开头会直接建立仓库和 PR 的映射：

```markdown
| 仓库 | PR |
|---|---|
| `goalfy-core` | [CodeUp PR](https://codeup.example.com/...) |
```

## 前置条件

- [ ] 当前环境能只读打开 CodeUp PR，或能访问对应 Git 远端。
- [ ] 至少提供一个 PR；如果 PR 没有关联需求，建议再提供一段需求背景。
- [ ] 需要写入仓库时，确认当前工作区中已有改动不会被覆盖。

## 边界

- 默认只创建 Markdown 文件，不修改 PR 描述，不自动发给同事。
- 不替 reviewer 给最终通过结论，也不自动评论、合并、commit 或 push。
- 根因只能由当前 diff 和证据支持；仅从代码推断或未核验运行时配置时会明确标注。
- 不覆盖同名旧文档，不复制凭据或大段未脱敏日志。

## Troubleshooting

| 问题 | 解决方法 |
|---|---|
| PR 涉及多个仓库 | 一次提供全部链接，文档会逐仓列出并分别核对 |
| 根因只能从 diff 猜到 | 文档会标“根据当前 PR 推断”；补充日志或项目信息后再升级结论 |
| 仓库里已经有同名文档 | 使用明确后缀保存，不覆盖已有文件 |

完整文档模板见 [SKILL.md](SKILL.md)。
