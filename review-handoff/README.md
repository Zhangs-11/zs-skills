# review-handoff

> PR 已经写完，但如果同事还要从零猜“为什么改、改了什么、重点看哪里”，Review 时间并没有真正省下来。

review-handoff 会读取一个或多个 CodeUp PR，并根据使用场景输出两种交接内容：群聊或 Review 邀请使用可直接复制的简略概要；需要同事独立理解完整链路时生成 Markdown 文档。两种模式都会先核对需求、真实 diff 和验证边界，不会把任务号、分支名或 PR 标题当成改动事实。

## 安装

```bash
npx skills add Zhangs-11/zs-skills --skill review-handoff
```

## 你可以这样说

- “这是本次改动的一组 PR，帮我生成一份 MD 给同事 review。”
- “按任务、需求、PR、验收项目和源分支，给我一段简略 Review 概要发群里。”
- “这个需求改了三个仓库，把仓库和 PR 都放在文档最上面。”
- “根据当前 diff 整理背景、问题根因和改前改后，重点提醒同事看状态恢复。”
- “我只给你这组 PR，你先从各仓库的代码和关联需求恢复上下文。”
- “同事可能不熟这块，请在文档里用一个具体订单 Case 把整条链路走一遍。”

## 你会得到

- 简略模式：结构化元信息、改动概要、1～2 个 Review 重点，以及必要的验证边界；
- 完整模式：可保存和转发的 Markdown 文档；
- 仓库与 PR 的清晰映射；
- 零背景也能理解的需求背景、问题和根因；
- 按业务链路整理的改动前/后表；
- 复杂链路下的一个具体 Case，注明输入、关键文件与方法、首次分叉和最终结果；
- 影响范围、已验证/未验证事项；
- 完整文档中的 2～4 个具体 Review 重点。

简略模式会直接返回：

```markdown
- 任务：`T-2878`
- 需求：`D-2373`
- PR：[GoalfyMax CodeUp #428](https://codeup.example.com/...)
- 验收项目：`899082222`
- 源分支：`fix/T2878-agent-plan-and-fa-cost/main`

改动概要：<问题、关键改动和保持不变的正常路径>。

请重点 Review：<1～2 个需要 reviewer 判断的点>。
```

完整文档开头会建立仓库和 PR 的映射：

```markdown
| 仓库 | PR |
|---|---|
| `goalfy-core` | [CodeUp PR](https://codeup.example.com/...) |
```

## 前置条件

- [ ] 当前环境能只读打开 CodeUp PR，或能访问对应 Git 远端。
- [ ] 至少提供一个 PR；如果 PR 没有关联需求，建议再提供一段需求背景。
- [ ] 需要写入仓库时，确认当前工作区中已有改动不会被覆盖。

## 边界

- 简略概要默认直接在当前对话输出；完整文档才创建 Markdown 文件。两种模式都不修改 PR 描述，不自动发给同事。
- 不替 reviewer 给最终通过结论，也不自动评论、合并、commit 或 push。
- 根因只能由当前 diff 和证据支持；仅从代码推断或未核验运行时配置时会明确标注。
- 不覆盖同名旧文档，不复制凭据或大段未脱敏日志。

## Troubleshooting

| 问题 | 解决方法 |
|---|---|
| PR 涉及多个仓库 | 一次提供全部链接，文档会逐仓列出并分别核对 |
| 根因只能从 diff 猜到 | 文档会标“根据已取得的 PR diff 推断”；补充日志或项目信息后再升级结论 |
| Case 没有真实运行数据 | 使用测试样例或明确标注的静态推演，不把构造输入写成线上事实 |
| 仓库里已经有同名文档 | 使用明确后缀保存，不覆盖已有文件 |

完整文档模板见 [SKILL.md](SKILL.md)。
