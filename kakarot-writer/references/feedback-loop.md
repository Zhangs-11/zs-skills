# 写作反馈闭环

这套流程把「AI 初稿到作者终稿发生了什么」变成可审查证据。它不从一次改稿直接推导长期文风，也不自动覆盖作者画像。

## 事实源与隐私边界

完整复盘时比较两个明确版本：实际交付给作者的初稿，以及作者确认完成的终稿。用户在对话中指出的具体错误、草稿箱验收发现和平台发布异常，也要作为独立反馈事件记录；它们不能被一次改稿报告吞掉。

初稿、终稿和差异报告可能包含未发布内容或个人经历。默认把它们放在当前任务的临时目录，不提交到公开仓库，不同步到长期规则。用户明确指定保存位置时再持久化。

## 生成机械差异

在 Skill 根目录运行：

```bash
python3 scripts/analyze_revision.py <初稿.md> <终稿.md> --output <临时目录>/revision-report.json
```

脚本只记录段落增删改、常见表达的数量变化和高频词变化。它不输出「作者喜欢短句」之类的语义结论，因为同一个差异可能来自篇幅限制、事实纠错、平台要求或本篇策略。

## 记录单次反馈事件

当用户指出「哪里写错了」「以后不要再这样」「草稿箱里出现了内部清单」时，不必等到拿到完整终稿。先把一句反馈拆成反馈原子：一条事件只能表达一个能被独立分类、归属和升级的主张；一句话里同时有事实纠错、本篇选择和长期偏好，就分别记录三条，不能共享同一个类别或 `explicit` 状态。

事件默认写入系统临时目录。`evidence` 与 `counterevidence` 只放不超过 500 字的脱敏摘要，不复制正文、私密经历或密钥。脚本默认拒绝写进任何 Git worktree；只有用户明确要求持久保存并确认目标仓库后，才可用 `--allow-repository-output` 覆盖。

例如：

```bash
python3 scripts/record_feedback.py \
  --article-id <文章标识> \
  --summary "正文重复标题" \
  --correction "标题只进入发布参数，不进入正文" \
  --category deterministic_error \
  --owner wechat-publisher \
  --status hard_rule \
  --scope "公众号发布" \
  --evidence "用户在草稿箱验收时指出" \
  --output <Git 仓库之外的任务私有目录>/feedback/<时间>-title-duplication.json
```

事件只保存必要摘要、修正规则、证据与反例，不默认复制整篇文章。分类固定为：

| 类别 | 含义 | 后续动作 |
|---|---|---|
| `deterministic_error` | 可客观判断的事实、链接、格式或发布契约错误 | 修正责任 Skill，补失败用例和回归测试 |
| `style_candidate` | 可能稳定的个人表达选择 | 进入候选，不自动提升为硬规则 |
| `one_off_choice` | 本篇标题、结构、篇幅或视觉选择 | 只影响当前作品 |
| `unknown` | 暂时无法判断原因 | 保留证据，必要时向作者确认 |

责任归属按最靠近错误生产机制的位置确定：事实、推断边界和作者声音归 `kakarot-writer`；正文清洗、标题重复、内部附录、图片路径和链接可达性归 `wechat-publisher`；比例、缩略图可读性和视觉溢出归 `visual-workflow`。不要把所有经验都堆进个人文风文件。

## 把差异分流

逐项读取初稿、终稿、用户原始要求和差异报告，把变化分到以下类别：

| 类别 | 处理方式 |
|---|---|
| 事实或亲历纠正 | 修正当前稿和相关事实源；不能当作语言偏好 |
| 本次明确要求 | 只服务当前作品，除非用户明确说以后都这样 |
| 平台或篇幅约束 | 记录适用平台与限制，不提升为跨平台个人风格 |
| 稳定声音候选 | 进入候选表，等待跨作品复现和作者确认 |
| 无法解释 | 标为未知，必要时一次问一个最能区分原因的问题 |

每条稳定声音候选至少写清：候选规则、初稿证据、终稿证据、可能的其他解释、适用范围、相反证据、出现于几篇相互独立的作品。

## 何时询问作者确认

用户明确说「以后都……」「这是我的固定偏好」时，这句话本身可以作为确认事实，但仍要检查它是否只针对某个平台或文体。

没有明确长期指令时，一次作品只能形成候选。候选在至少两篇相互独立的作品中重复出现，且没有同等强度的反例后，才向作者提出一个确认问题。脚本必须记录独立的 article IDs；只有作者确认后，才能用 `author_confirmed` 把它提升为硬规则。整数次数本身不是独立作品证据。每次只确认一条规则，并同时给出支持证据、适用边界和最强反例。

不要把「作者没改」当作偏好证据。作者可能没看见、没时间改或认为这次无关紧要。

客观可判定的错误不需要等待两篇作品复现。确认错误后，立即把规则放进对应生产或发布机制，并补一个能在旧错误上失败、在修复后通过的回归测试。规则只有说明文字、没有执行点或测试，不算完成沉淀。

## 确认后怎样进入长期规则

确认前不得修改 `references/personal_voice.md`、`references/style_examples.md` 或其他长期画像。

确认后做最小更新：

1. 把规则写成能指导选择的机制，不收集口头禅。
2. 写明适用文体、平台或场景，以及已知例外。
3. 用作者确认的终稿片段作为事实来源，但只摘必要短句或概括机制。
4. 增加至少一个正向评测和一个反例评测，防止新规则被过度应用。
5. 运行 Skill 校验和现有评测；先让作者 review，再按当前授权决定是否提交。

每次迭代都要能回答四个问题：这条经验来自哪次反馈；它属于事实、风格还是平台契约；哪个 Skill 负责执行；哪个测试能阻止复发。缺少任一项时，只能保留为候选，不能声称系统已经学会。

若新规则与既有规则冲突，不按时间新旧直接覆盖。展示冲突证据，确认是替换旧规则、缩小双方范围，还是保留为不同文体的两种选择。
