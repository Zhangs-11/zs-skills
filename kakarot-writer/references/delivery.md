# 完整长文交付

用户说“帮我写篇文章”时，默认按本文件完成全部交付。生成不等于发布，外部写入仍需用户明确要求。

## 主稿

交付一个平台中性的 Markdown 内容母稿。公众号、知乎、博客、掘金和B站专栏同步时，标题、正文、核心图片和核心判断保持一致。

小红书、抖音和B站视频也使用这份母稿作为唯一内容源。它们可以调整标题长度、段落密度、口播节奏、字幕和画面顺序，但事实、案例、核心判断、作者态度和来源都必须回指母稿，不能再写一套内容。

小标题按材料决定。强叙事可以一口气写到底；经验方法和信息密集的文章可以用 `##` 分区。不要为了套公众号格式制造小标题。

只使用各平台都能稳定渲染的基础 Markdown。重要判断可以克制使用 `**加粗**`，一篇通常不超过三到五处；不要使用 `==高亮==`、平台私有组件或依赖特定博客引擎的语法。

### 母稿、公开正文与交付附录

同一个 Markdown 文件可以服务编辑与发布，但三个消费者的边界必须明确：

1. 标题、作者、摘要等元数据由发布命令或规范的文件元数据承载，不作为正文段落。
2. 公开正文从第一段正文直接开始，不重复写 `# 文章标题`。
3. 只供作者和发布流程使用的截图清单、封面文件、备选标题、事实确认项和交付说明，统一放到以下精确标记之后：

```markdown
<!-- kakarot:delivery-appendix -->

## 截图清单
...
```

发布工具必须在格式化、摘要提取、图片上传和链接检查之前切掉交付附录。不要用普通 `---` 充当边界，因为它也可能是正文分隔符或 YAML frontmatter。

## 标题

正文完成后给出三个候选：

1. 冲突型，突出真实存在的张力。
2. 发现型，突出作者通过经历或研究看到的新东西。
3. 收益型，告诉读者读完能解决什么问题。

推荐其中一条，并说明一句选择理由。标题必须被正文完整兑现，不能暗示不存在的实测、内幕和极端结果。

## 图片与截图

引用推文、GitHub issue、官方公告、产品页面、研究报告和新闻原文时，使用：

```markdown
[插图：用户截图 - 页面或内容说明]
> GitHub地址：github.com/owner/repo/issues/123
```

来源前缀写明平台，如 `X推文地址`、`GitHub地址`、`官方公告地址`、`论文地址`。文章末尾提供截图清单，列出位置、用途和完整链接。

先判断图片承担的是证据、解释还是氛围作用：

- 产品体验、教程、新闻、数据、评测和工具文章优先使用真实截图、实拍照片、官方图和原始页面；证据图不能被 AI 图替代。
- 解释关系、流程和责任分工时，按 [公众号解释型图文](visual-storytelling.md) 交付渲染图、可编辑源和手机预览；文字只补图未表达的内容。
- 无字 AI 主视觉用于必要的抽象表达或转场，一篇通常不超过一至两张，不能代替解释图或被当成真实产品、实验现场和数据结果；这个数量建议不限制承载信息的流程图、结构图与截图。

不要生成假 UI 代替真实页面，也不要在 AI 图中生成产品 Logo、中文标题、数据和需要被读者当真的界面文字。

### 正文叙事配图

完整文章默认在封面之外评估并制作有助于理解段落的叙事插画；用户只要求文字或局部修改时，遵从其范围。正文叙事配图与封面统一优先使用 `baoyu-cover-image`；不可用时按本文件“封面”一节回退到 `guizang-social-card-skill`，两者都不可用时使用通用图像生成流程。同篇文章复用封面实际采用的生成方法，保持配色、笔触和人物表现一致，构图围绕当前段落重新设计；正文配图的尺寸与文字安排仍按本节要求执行。

先确定插入位置、段落核心含义和读者通过画面应理解的一个重点，再把这个重点转化为具体场景、动作或人物关系。每张图只解释一个重点，数量按内容决定，可以有多张，不设固定配额；帮助理解的叙事插画不受纯氛围图一至两张的建议限制。精确流程、数据与责任关系仍按 visual-storytelling.md 制作可核对的解释图，事实证据仍使用真实素材。

生成后实际查看图片，核对画面是否表达段落原意、是否引入原文没有的能力或事实，以及手机宽度下主体是否清楚。配图使用适合正文单列阅读的构图，不照搬封面的标题和海报布局。将成品通过 Markdown 图片引用放在对应段落附近，写明描述性 alt；必要时用简短图注标明概念示意，避免被当作真实现场。交付真实图片文件，不只交付提示词或占位符。

## 重点区块与公众号样式

提示词、操作模板、关键结论和风险提醒需要读者特别关注时，使用有明确标题的重点区块；普通叙述保留正文，不把每段都卡片化。按语义区分：可复制材料用浅色底与强调边框，结论用短句加粗，风险提醒用「注意」等文字标签搭配警示色。全篇保持同一主色，颜色不能成为唯一的信息提示，避免浅色字、满屏强调和装饰性 UI。

提示词和命令保留可选择复制的原生文字，字号与正文接近，长链接自然换行，不用截图、小字代码长条或不可用的「复制」按钮代替。长模板按段组织，不为省高度折叠、截断或缩字。母稿用基础 Markdown 的标题、引用、列表或代码块表达语义，去掉样式后内容仍完整；不引入平台专属 alert 语法。

公众号排版优先单色背景、边框和留白。交付用于复制或发布的 HTML 时，将字号、行高、颜色等必要样式写到具体元素的行内 style，不仅依赖页面 style、class 或父容器继承；不依赖脚本、悬停、伪元素、动画或复杂布局。保留真实图片和来源链接，不照搬参考项目的图片占位或标点改写。浏览器预览与公众号实际清洗后的呈现分别验收，未进后台只报告本地预览结果。

有重点区块时，在 360/390 px 视口检查文字可读、长链接不溢出、复制内容完整，并做去样式检查；没有重点材料的文章不增加区块。此规则借鉴 [dbs-wechat-html](https://github.com/dontbesilent2025/dbskill/tree/main/skills/dbs-wechat-html) 的行内样式与稳定 CSS 子集，以及 [baoyu-markdown-to-html](https://github.com/jimliu/baoyu-skills/tree/main/skills/baoyu-markdown-to-html) 的主题与提示块分工；仅整合原则，不安装依赖或照搬整套风格库。

## 封面

完整文章默认生成：

- `21:9` 微信公众号主封面。
- `1:1` 分享封面。

默认采用 `baoyu-cover-image` 的叙事插画路线：

- 先提炼文章中一个具体的矛盾、人物关系或机制，不把产品名和关键词直接堆成海报。
- 主视觉必须表现动作或关系，例如模型正在参与研发、工程师把能力带入真实业务、现场结果回流到产品团队。
- 标题放在清晰留白区，正文只保留一个主标题和少量识别标签；不生成泛化的 AI 科幻背景、孤立 Logo、假 UI 或信息面板。
- 21:9 与 1:1 分别构图；1:1 使用短标题和单一主动作，不能把横版封面直接裁成方形。

若 `baoyu-cover-image` 不可用，再按文章类型选择 `guizang-social-card-skill` 的素材路线：

- 产品发布、工具体验、教程和评测：优先使用官网、官方文档、公告、GitHub、真实产品截图或作者实拍，并把外部素材来源写入 `assets/SOURCES.md`。
- 抽象概念、趋势判断和技术原理解读：现实素材不足以表达核心冲突时，默认选择 AI 生成路线，无需重复询问 A/B/C。这是 Kakarot 已经确认的长期偏好。

AI 封面使用两段式流程：

1. 优先调用当前可用的图像生成工具，生成无字、无 Logo、无假 UI 的主题主视觉；提示词围绕文章核心冲突、视觉隐喻、主体位置和标题安全区编写。
2. 再由封面排版流程添加标题、作者信息和必要标注，分别编排 `21:9` 与 `1:1`，不要让图像模型一次性生成带中文标题的成品海报，也不要机械裁切复用。

图像生成工具不可用时，优先用可验证的真实素材完成封面；两者都不足时才使用纯排版封面，并在交付说明中说明限制。无论采用哪条路线，封面视觉都必须服务于文章真实结论，不能虚构产品能力、实验结果或现场。

## 跨平台尾部

正文默认使用跨平台通用尾部，不出现只适用于微信的“点在看”“星标公众号”和“公众号推荐机制”。根据文章选择一种：

- 提问互动，邀请读者分享自己的经历。
- 价值确认，邀请点赞、收藏和评论。
- 克制收尾，正文已经有足够余韵时不额外添加互动号召，只保留固定尾部。

默认固定尾部：

```markdown
> / 作者：kakarot
> / 投稿、合作或交流，欢迎在公众号后台留言
```

“公众号后台留言”是稳定联系入口，可以保留在跨平台母稿中；“点在看”“星标公众号”等平台操作仍只在用户明确要求公众号专属版本时追加。

## 交付链接验收

交付预览、图片或下载文件前，逐个验证最终发给用户的链接，而不只检查磁盘文件存在。按当前界面的真实解析规则确认相对路径、工作目录和访问边界；HTTP 链接实际 GET 后核对状态及响应内容，避免把登录页或错误页的 200 当成成功。HTML 预览还要检查引用图片是否加载。不能用工具可读取文件代替用户界面可访问，也不能靠关闭安全边界修复链接。

无法验证用户端访问时明确说明限制，不称链接已可用。临时本地服务须说明仅本机可用且依赖服务持续运行，只服务交付所需目录；不把本地地址当成远程用户可访问的链接。修复后重新验证最终链接再交付。

## 最终交付顺序

1. 推荐标题与两个备选标题。
2. 完整 Markdown 正文。
3. 封面文件或可点击路径。
4. 标记后的截图清单、封面文件与内部交付信息；希望读者看见的“关键来源”可以保留在公开正文中。
5. 必要的事实确认项。

默认不附内部提纲和机器质检报告。
