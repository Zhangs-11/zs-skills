# project-aware-coding

> AI 很容易写出“语法正确、看起来标准”，却不适合当前项目真实链路的代码。

project-aware-coding 会在实现需求、修 Bug 或修改接口前，先参考项目里最接近的现有逻辑、测试、设计说明和历史修复，理解它们曾解决过什么问题，再完成贴合当前消费者的最小改动。它不会把旧代码当成不可违背的规则：旧实现不适用于新需求、版本或消费者时，可以有证据地采用不同方案。

## 安装

```bash
npx skills add Zhangs-11/zs-skills --skill project-aware-coding
```

## 你可以这样说

- “参考这个项目现有接口的写法，帮我给订单取消增加原因字段。”
- “修一下这个 Bug，先看看项目是不是已经在别处处理过相同情况。”
- “给 MCP 工具补参数 Schema，但要先确认项目的模型和注册链路实际支持哪些写法。”
- “旧接口一直返回字符串 ID，不过新客户端支持数字；请核对真实消费者后再决定是否沿用。”

## 它会怎样工作

1. 读取当前仓库的 `AGENTS.md`、`CLAUDE.md`、项目级 Skill 和必要开发说明，并检查工作区是否已有其他改动。
2. 追踪本次需求的入口、状态变化、真实消费者、结果及失败或恢复路径。
3. 按风险寻找最接近的项目样本：简单局部修改通常参考一处邻近实现；协议、Schema、序列化、跨服务接口、并发和兼容改动会继续检查相关测试和必要历史。
4. 理解旧设计为什么存在，再决定复用还是有理由地偏离，最后只实现当前需求需要的最小范围。
5. 沿同一条真实消费链路运行目标测试、边界样例和仓库要求的检查，并明确仍未验证的事实。
6. 基于本次最新完整 diff 使用 `peer-pr-review` 独立自审；原需求范围内有证据的必须项会自动修复、重新验证并完整复审，直到没有仍需修复的问题再交付。

例如，JSON Schema 标准允许某个关键字，不代表当前模型、SDK、网关或工具注册链路一定支持。Skill 会优先核对项目实际消费者和历史兼容经验；但如果新版本已经支持，也不会因为旧代码没用过就机械拒绝，而是通过针对性测试后采用新写法。

## 前置条件

- [ ] 当前环境可以读取并修改目标 Git 仓库。
- [ ] 仓库已有项目说明、规范或同类代码时，当前账号可以读取它们。
- [ ] 需要验证远端分支、外部协议或运行环境时，具备相应只读权限和测试条件。
- [ ] commit、push、部署、数据库写入等动作已另行授权；普通实现请求不会自动授权这些操作。

## 你会得到

- 与需求和真实根因直接对应的最小代码改动；
- 实际影响方案的项目参考实现及其设计理由；
- 针对当前消费者的测试和检查结果；
- 最终完整 diff 的自审结论，以及自审后自动修复的问题；
- 无法验证但可能影响正确性的关键缺口。

## 边界

- 项目已有实现是高价值参考，不是绝对正确答案。
- 找不到可靠样本时，会说明搜索范围，转而读取真实消费者、官方当前契约或执行最小验证，不会随便抄名字相似的代码。
- 不会为了让测试通过而放松断言、跳过测试或隐藏错误。
- 自审建议项、低概率隐患和超出原需求的重构不会被顺手修改；涉及范围或行为选择时仍会先征求确认。
- 不混入无关格式化、顺手重构、依赖升级和未来兼容设计。
- 不自动删除已有文件、函数、注释、测试或兼容逻辑。

## Troubleshooting

| 问题 | 解决方法 |
|---|---|
| 仓库里搜不到同类实现 | 提供真实调用入口或消费者；Skill 会记录搜索范围，并改用官方契约或最小运行探针验证 |
| 项目旧写法和新需求冲突 | 补充版本、消费者或兼容要求；Skill 会区分哪些约束仍成立，再决定是否偏离旧设计 |
| 测试绿了但仍不确定能否上线 | 提供实际部署环境或协议链路；本地测试不会被冒充成线上事实 |
| 工作区已有其他人的改动 | 保留并避开未知改动；无法安全隔离时会先说明冲突范围 |

完整执行流程见 [SKILL.md](SKILL.md)。
