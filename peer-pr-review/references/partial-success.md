# 部分成功门禁：写入后失败必须有恢复闭环

只要控制流在已创建资源、写库、发消息、调外部接口或产生其他持久副作用后仍可能返回 `success=false`，就不能把它当作“未执行”。先列出每个写入后失败点，再逐项证明最终状态和调用方的下一步。

1. **确认剩余状态**：失败后资源是在线、离线、pending、部分绑定还是未知；不得只因返回值是失败就忽略已产生的对象。
2. **证明清理或同资源恢复**：要么已安全回滚，要么返回调用方真能执行的稳定资源 ID、恢复入口和结构化参数。文案说“检查后上线”不等于有恢复入口；`retry_action` 只有在对应工具真实存在并能沿用同一 ID 时才算完整。
3. **反向测试重试**：使用同一输入重试失败步骤，核对创建次数、新 ID 数量和全部副作用。必须读取真实幂等键、唯一约束、重名检查或工单恢复契约；不得根据字段名或其他资源的幂等实现推断当前创建链安全。
4. **对照仓库恢复先例**：查找同类“对象已建好、后续阶段失败”的返回契约和恢复工具。偏离现有的同 ID 恢复方式时，要用更强证据证明新设计不会制造孤儿、重复对象或无法到达的终态。

写入后失败只返一句人话、只把 ID 放在没有真实消费者的字段里，或建议重跑创建却没有幂等保护时，结论至少为“基本合理，需补充”；已能静态推出重复写入或孤儿状态时，应判为“需要修正”。
