# peer-pr-review

> 同事给你一个陌生需求和 CodeUp PR，不需要先花半小时考古，也不需要相信 PR 里写的根因一定正确。

peer-pr-review 会先固定真实 diff，再沿上下游、规范和可用运行时证据独立核验根因，并用横向链路图和真实代码证据展示改动前后的变化，最后输出一份零背景也能读懂的短 Review。默认只展开最多 3 个真正影响合并决定的问题。

## 安装

```bash
npx skills add Zhangs-11/zs-skills --skill peer-pr-review
```

## 你可以这样说

- “同事让我帮忙 review，背景是……，PR 是这个 CodeUp 链接。”
- “帮我看看这个 PR 的根因判断和修复有没有问题，QA 项目 ID 是 12345。”
- “我不熟这块代码，先把需求讲明白，再告诉我能不能过。”
- “同事说是缓存问题，但我不确定，你独立核验一下。”

## 最低输入

- 需求背景；
- CodeUp PR 链接。

项目 ID、环境、日志、OA 编号和同事方案都是可选信息。缺少运行时信息时仍会完成静态审查，但不会把最新代码或默认配置冒充成线上事实。

## 前置条件

- [ ] 当前环境能只读打开 CodeUp PR，或能访问对应 Git 远端。
- [ ] 用户已提供需求背景和 PR；如有 project ID、环境和复现步骤，建议一并提供。
- [ ] 若结论依赖 Nacos、数据库、Hub 或日志，当前账号具备相应只读权限。

## 你会得到

- 两三句话的需求背景与问题描述；
- 独立根因判断，以及和同事判断是否一致；
- 改动前/后的横向主链路，复杂判断按需单独展开；
- 能追溯到仓库、文件、函数、行号和版本的关键代码证据；
- 最多 3 个有证据、可行动的阻塞或建议项；
- 已验证事实和仍未验证的关键缺口。

输出会先给结论，再用一张表对比同事判断和独立复核：

```text
结论：基本合理，需补充
根因：同事找对了直接原因，但真正的首次偏离发生在状态写入层。
改动：新逻辑能修正主路径；恢复路径仍缺同一状态门禁。
```

复杂链路不会被塞进一张完整控制流图：主图只保留 5～8 个业务阶段，复杂 `if/else` 另画局部判断图；简单单点改动则直接使用对比表，避免为了画图增加阅读成本。

## 边界

- 默认只读，不修改代码，不在 CodeUp 评论、通过或合并 PR。
- 涉及远端现状时先检查工作区并更新远端引用，不覆盖未知改动。
- 数据库只做只读查询；不输出凭据、完整 Prompt 或未脱敏业务数据。
- PR 无法访问时会请求 patch 或仓库/分支信息，不根据标题假装完成审查。

## Troubleshooting

| 问题 | 解决方法 |
|---|---|
| CodeUp 页面无法访问 | 提供可读 patch，或仓库、源分支、目标分支和 PR commit |
| 只有静态代码，无法确认线上根因 | 补充环境、project ID 或部署版本；报告会先标“运行时未验证” |
| 输出太长 | 要求保留结论、根因对比、改前改后和最多 3 个正式问题 |

完整审查流程和输出模板见 [SKILL.md](SKILL.md)。
