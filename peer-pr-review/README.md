# peer-pr-review

> 同事给你一个陌生需求，或者你想在提交前审查自己的本地改动，都不需要先花半小时考古，也不需要默认改动者写的根因一定正确。

peer-pr-review 支持 CodeUp PR、当前 Git 工作区、本地分支和独立 worktree。它会先固定真实基线与 diff，再独立核验根因，并把关键术语、方法用途和改动前后链路翻译成业务白话，最后输出一份第一次接触项目也能读懂的短 Review。

## 安装

```bash
npx skills add Zhangs-11/zs-skills --skill peer-pr-review
```

## 你可以这样说

- “同事让我帮忙 review，背景是……，PR 是这个 CodeUp 链接。”
- “帮我看看这个 PR 的根因判断和修复有没有问题，QA 项目 ID 是 12345。”
- “我不熟这块代码，先把需求讲明白，再告诉我能不能过。”
- “同事说是缓存问题，但我不确定，你独立核验一下。”
- “帮我 review 一下当前仓库还没提交的改动。”
- “审一下这个 worktree 里的全部改动，目标分支是 main。”
- “这个 PR 之外我又改了几处，分别告诉我哪些属于 PR、哪些还在本地。”
- “我不懂这里的术语和方法，按新手能听懂的方式解释后再给结论。”

## 最低输入

- 一个可定位的审查对象：PR、当前工作区、worktree、分支、commit 或 patch；
- 需求背景；若可从当前对话、关联工作项或代码可靠恢复，也可以不重复提供。

项目 ID、环境、日志、OA 编号和改动方案都是可选信息。缺少运行时信息时仍会完成静态审查，但不会把最新代码或默认配置冒充成线上事实。

## 前置条件

- [ ] 当前环境能读取目标 Git 仓库、worktree 或 CodeUp PR。
- [ ] 分支/worktree 审查能确定目标分支；当前未提交改动默认比较 `HEAD → 工作区`。
- [ ] 如有 project ID、环境和复现步骤，建议一并提供。
- [ ] 若结论依赖 Nacos、数据库、Hub 或日志，当前账号具备相应只读权限。

## 你会得到

- 两三句话的需求背景与问题描述；
- 只解释本次必需的关键术语，不用陌生词循环解释；
- 独立根因判断，以及和改动者判断是否一致；
- 上下排列的改动前/后两张主链路图，每张图内部从左到右展示，复杂判断按需单独展开；
- 关键方法由谁调用、输入什么、做什么、产出什么，以及为何与问题有关；
- 按风险参考项目中最接近的同类实现、测试和历史修复，说明哪些既有设计经验影响了判断，但不机械照搬旧代码；
- 能追溯到仓库、文件、函数、行号和版本的代码证据；
- 最多 3 个有证据、可行动的阻塞或建议项；
- 多入口需求会核对“入口 × 输入/状态 × 完整输出/副作用”覆盖矩阵，特别检查能同时出现的混合异常；
- 新增校验器或解析器时，会对照真实消费者操作，双向检查“上游放过但下游拒绝”和“下游能处理但上游误拒绝”；
- 两层使用不同语言或库时，会用同一组标准、兼容、非法和边界输入实测，避免把同名方法和测试绿灯误当成契约一致；
- 部分更新会合并存量配置再完整校验时，会专门验证“合法旧配置 + 只改无关字段”，防止新增门禁阻断历史数据；
- 逐个 diff hunk 核对是否为需求、根因或必要测试服务，识别无意义空行、格式噪音、顺手重构和未来设计；
- 删除注释、测试或错误处理前要求失效证据，保护仍正确且有解释价值的原有内容；
- 已验证事实和仍未验证的关键缺口；
- 最后按条给出完整的建议改动，说明改哪里、为什么、怎么改以及如何验证。

输出会先给结论，再用一张表对比改动者判断和独立复核：

```text
结论：基本合理，需补充
根因：改动者找对了直接原因，但真正的首次偏离发生在状态写入层。
改动：新逻辑能修正主路径；恢复路径仍缺同一状态门禁。
建议：在恢复路径复用主流程的状态门禁，避免失败重试绕过同一约束；同时补充一次重复投递测试，确认只产生一次业务结果。
```

改动前和改动后不会被塞进同一张图：两张图按上下顺序展示，并使用相同阶段和编号逐项对照。每张主图只保留 5～8 个业务阶段，复杂 `if/else` 另画局部判断图；简单单点改动则直接使用对比表，避免为了画图增加阅读成本。

## 边界

- 默认只读，不修改代码，不在 CodeUp 评论、通过或合并 PR。
- 涉及远端现状时先检查工作区并更新远端引用，不覆盖未知改动。
- 本地审查会分别读取 staged、unstaged 和相关 untracked 文件，不切分支、不 stash、不改 index。
- PR 和本地额外改动同时存在时分开标记，避免把尚未进入 PR 的代码算进 PR 结论。
- “请求被拒绝”“主流程通过”或“测试绿灯”不自动等于完整契约通过；关键矩阵格子未验证时不会下“没有其他问题”的结论。
- 校验器、Schema、解析器与真实消费者会按接受输入集合双向对照；不同库必须跑同一组边界样例。
- 项目现有写法会作为高价值参考，而不是不可违背的规则；如果新方案有明确的新需求、版本或消费者差异，可以采用不同实现，但要给出针对性验证。
- 合并存量配置后触发完整校验的更新路径，必须覆盖无关字段更新，避免兼容性回归。
- 修正上一轮问题后的复审会重新固定最新 patch set 并重审完整矩阵，不只回归上一条评论。
- 测试通过不能替无关改动正名；无法映射到当前需求的 hunk 会被标为范围外，建议移除或拆分。
- 数据库只做只读查询；不输出凭据、完整 Prompt 或未脱敏业务数据。
- 审查对象无法访问或比较基线不明确时会请求最少的必要信息，不根据标题或描述假装完成审查。

## Troubleshooting

| 问题 | 解决方法 |
|---|---|
| CodeUp 页面无法访问 | 提供可读 patch，或仓库、源分支、目标分支和 PR commit |
| 不知道 worktree 应该和哪个分支比较 | 明确目标分支；Skill 不会在多个合理基线中擅自选择 |
| 普通 `git diff` 看不到新文件 | Skill 会额外读取相关 untracked 文件，并在范围中列明 |
| 只有静态代码，无法确认线上根因 | 补充环境、project ID 或部署版本；报告会先标“运行时未验证” |
| 输出太长 | 要求保留结论、根因对比、改前改后和最多 3 个正式问题 |

完整审查流程和输出模板见 [SKILL.md](SKILL.md)。
